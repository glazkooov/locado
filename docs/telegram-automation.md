# Восстановление Telegram-автоматизации

Подготовлено 10.11.2026. **Оба расписания выключены**, ничего не отправлено.
`tools/automation/telegram-routines.json` — спецификация для проверки владельцем,
а не установленный планировщик и не обещание совместимости с API импорта.

| Задача | Москва | Cron с Europe/Moscow | Cron для планировщика только с UTC |
|---|---|---|---|
| Ежедневные черновики | 09:37 каждый день | `37 9 * * *` | `37 6 * * *` |
| Недельный разбор | 10:41 по понедельникам | `41 10 * * 1` | `41 7 * * 1` |

Москва использует UTC+3 без сезонного перевода. Не задавать одновременно
московское время и UTC-сдвиг. После включения возможны задержки планировщика;
точную минуту доставки нельзя обещать. Пропущенные исторические запуски не
догонять автоматически, разовые задачи из экспорта не восстанавливать.

## Что исполняет каждое задание

**Ежедневное** должно запускать агента с доступом к репозиторию. Скрипт
`tools/telegram.mjs` выбирает кандидатов, форматирует и отправляет готовый
JSON; сам он текст не сочиняет. Shell cron, который запускает один `pick`,
не восстанавливает задачу. Полный prompt: `tools/automation/daily.md`.
Результат запуска: три согласованных по темам черновика владельцу, пометки
утро/день/вечер и сохранённый журнал. В канал ничего не отправляется.

**Недельное** запускает `node tools/telegram-stats.mjs --send`. Скрипт читает
публичное превью `t.me/s/locado_msk`, сохраняет снимок и отправляет сводку
владельцу. Prompt и порядок восстановления после сбоя:
`tools/automation/weekly.md`. API Метрики не вызывается: ссылка в отчёте не
требует токена Метрики. Малые числа не дают надёжных выводов о рубриках.

## Зависимости, секреты и настройка

| Требование | Где настроить | Для чего |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` (секрет) | Secrets облачной среды, выбранной для будущих задач, с передачей в переменную процесса; разрешённый HTTPS-host `api.telegram.org` | Bot API: личные черновики и сводка |
| Тот же токен при выборе GitHub Actions для недельной задачи | Repository → Settings → Secrets and variables → Actions → Repository secrets | Только если этот runner будет выбран; workflow пока не добавлен |
| `api.telegram.org`, `t.me` | Internet access / разрешённые домены выбранной среды | Bot API и чтение публичной статистики; не копировать токен в URL команд или логи |
| Git read/write выбранной ветки | Встроенная GitHub-интеграция runner | Сохранение журнала и снимков; HTTPS read уже работает через платформу, отдельный PAT для него не нужен |
| Node.js 22+ и Playwright/Chromium | `tools/cloud/install.sh`, `docs/development.md` | Node API `Object.groupBy`; картинки схем и альбомов |

На момент проверки в работающем процессе токен **отсутствует**; в metadata
среды секретов и runtime variables тоже нет. `tools/telegram.json` уже содержит
личку владельца и `@locado_msk`; это идентификаторы, не токен. Повторять `setup`
не нужно, если они верны. Если личка перестала работать, владелец пишет боту
`/start`, затем по отдельному разрешению выполняется `setup @locado_msk`.
Для отправки в канал бот должен быть администратором с can_post_messages;
это не проверялось и для подготовки документов не требуется.

Скрипт подставляет токен в **путь URL** Bot API. Если среда предоставляет
proxy-placeholder вместо значения, совместимость такой подстановки нельзя
предполагать: проверить `getMe` без вывода URL/токена до первой отправки.
Секретные значения вводятся только через настройки, не в чат и не в Git.
Не запрашивать другие API-ключи, пока не выбран runner и они ему не нужны.

`TEST_FTP_SERVER`, `TEST_FTP_USERNAME`, `TEST_FTP_PASSWORD` относятся только
к существующему деплою тестового сайта и задаются в GitHub Actions Secrets.
Для Telegram и локального сайта они не требуются.

## Что проверить перед включением

1. Владелец увидел эту спецификацию и явно разрешил включение двух задач;
   сейчас такого разрешения нет. Доступного инструмента создания агентных
   расписаний в этой сессии также нет. Само наличие JSON ничего не включает.
2. Выбран постоянный runner, timezone и **одна** ветка состояния. Предложение:
   `claude/telegram`, с аккуратным внесением свежего `main` перед запуском.
   Не сбрасывать ветку на старый snapshot, не пушить зеркально в две ветки.
   Свежие восстановленные изменения сначала должны попасть в эту ветку.
3. Проверены наличие токена, свежий `getMe`, доступ к `t.me`, права Git write;
   Bot API send и чтение публичного канала в этой миграции не запускались.
   Запуск `telegram-stats.mjs` **без `--send` тоже пишет снимок**, это не dry run.
4. После разрешения на пробную доставку проверить один черновик владельцу
   и один недельный отчёт. Сверить фактическую доставку, snapshot и Git-коммит;
   лишь затем включать повторение. Не использовать `publish` для smoke test.
5. Два задания и ручная работа не пишут журнал параллельно. Нужна общая
   блокировка по репозиторию/ветке (например concurrency group runner).
   Встроенной транзакции отправки+записи в Git в скриптах нет.

При ошибке Git push после отправки нельзя повторять отправку: сохранить
файлы и восстановить только Git-запись. При сетевом обрыве после POST статус
доставки неизвестен, сначала свериться с владельцем. В недельном скрипте
снимок пишется **до** send; повтор с `--send` может повторить сообщение.

## Уже существующая автоматизация

- `.github/workflows/photos.yml`: push фото в main или ручной запуск,
  сжатие Pillow и Git-коммит. Не скачивает отсутствующие фотографии.
- `.github/workflows/deploy-test.yml`: push `claude/**` или ручной запуск,
  FTP на тестовый сайт. Это не публикация production, нет шага `npm run check`.
- Telegram-расписаний в `.github/workflows` нет. Ранее они жили в Claude,
  а не в Node-скриптах и не в системном cron этой машины.
- Строки «расписание сделано» в старой документации не означают, что задачи
  активны в новой среде. Публикация production остаётся ручной у владельца.
